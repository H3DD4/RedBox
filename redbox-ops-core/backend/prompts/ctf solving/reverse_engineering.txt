<possible_scenarios>
You may encounter these situations:

1. **Flag in Strings**: Flag is visible with `strings` command
2. **Simple Comparison**: Input compared directly to hardcoded flag
3. **Transformation Required**: Input transformed (XOR, ROT, Base64) before comparison
4. **Custom Algorithm**: Proprietary encryption/encoding implemented
5. **Obfuscated Code**: Control flow flattened, junk code inserted
6. **Packed Binary**: UPX or custom packer used
7. **VM-based**: Custom virtual machine interprets bytecode
8. **Multi-stage**: Multiple binaries or stages to decode
9. **Keygen Required**: Must understand algorithm to generate valid input
10. **Dynamic Generation**: Flag generated at runtime, not stored
</possible_scenarios>

<macro_steps>
Follow this methodology using MCP tools:

1. **Initial Triage**
   - Use file analysis tools to identify binary type
   - Extract strings and analyze entropy
   - Detect packing/obfuscation

2. **Static Analysis**
   - Disassemble/decompile to understand program flow
   - Identify main function and input handling
   - Locate comparison/validation logic
   - Extract hardcoded data and constants
   - Identify encryption/encoding routines

3. **Dynamic Analysis**
   - Use debugger tools to trace execution
   - Set breakpoints at key functions
   - Monitor registers and memory during validation
   - Extract runtime-generated values

4. **Algorithm Reconstruction**
   - Reverse custom algorithms using analysis tools
   - Convert to Python/C for testing
   - Validate against binary behavior

5. **Flag Extraction**
   - Apply reversed algorithm to ciphertext
   - Generate valid input
   - Extract flag from memory or calculation
</macro_steps>

<deliverable>
Provide a clear solution including:
- Vulnerability/technique identified
- Step-by-step reverse engineering process
- MCP tools used at each stage
- Code used to extract/decrypt flag
- Final flag (format will be provided as variable)
</deliverable>
